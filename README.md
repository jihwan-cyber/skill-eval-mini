# skill-eval-mini

AI 에이전트의 **스킬 선택**을 평가하고 자동으로 개선하는 축소판 실험입니다.
라우터 모델은 각 스킬의 `name`과 `description`만 보고, 사용자 요청마다 스킬 하나 또는 `none`을 고릅니다.

> **한 줄 요약**: 라우터(Claude Haiku 5.5)가 스킬을 고르는 방식을 평가하고, 자동 개선 루프로 고친 뒤, **외부 사람이 쓴 실제 요청으로 다시 검증**했습니다.
> - 직접 만든 테스트셋에서는 자동 개선으로 정확도를 **91.7% → 100%** 로 올렸습니다(오발동 16.7% → 0%).
> - 하지만 외부 참여자 3명이 쓴 **실제 요청 30개**에서는 **원본이 100%로 가장 좋았고**, 개선본은 93~97%로 오히려 떨어졌습니다. 비용도 최대 2.4배였습니다.
> - 개선 규칙("도구 사용법 질문이면 none")이 "엑셀 자동 계산되게 해줘" 같은 정상 요청까지 막았습니다. **직접 만든 테스트셋에 맞춘 개선이 실제 사용에서는 역효과**를 낸 것입니다.
> - 그래서 외부 요청을 **검증셋**으로 써서, 검증셋 점수가 떨어지는 수정안은 거절하게 바꿨습니다. 이 안전장치는 "엑셀" 같은 회귀를 막았습니다.
> - 하지만 검증셋에 없던 유형의 오답은 막지 못했고, 같은 설정으로 두 번 돌려도 결과가 달랐습니다.
> - 마지막으로 외부 참여자 2명에게 **작업 요청 20개**("이 코드 왜 오류 나?", "이 표 순위대로 정리해 줘" 등)를 따로 받아 확인했습니다. 원본과 개선본 모두 100%였고, 지시문을 바꾼 개선본은 비용만 2.2~2.5배였습니다.
> - 그런데 실험을 진행한 본인의 **과거 대화 기록 33개**에서는 결과가 뒤집혔습니다. 원본은 89.9~93.9%였고 처음 자동 개선한 설정이 99%였습니다. 반면 검증셋 기준으로 채택된 지시문은 83.8%로 가장 나빴습니다.
> - 모든 실제 데이터에서 반복된 오답은 하나였습니다. **"조사해서 알려줘", "정리해서 알려줘" 같은 요청이 report_write나 summarize로 새는 것**입니다. 이런 요청을 맡을 검색·조사 스킬이 없어서 가장 가까운 스킬로 밀려가는 것으로 보입니다.
> - 그래서 **검색·조사 스킬(web_research)을 추가**했습니다. 정답 기준은 결과를 보기 전에 먼저 정해 저장소에 올렸습니다(`LABELING.md`). 조사 요청은 거의 모두 새 스킬로 갔고, 반복되던 report_write 오답은 사라졌습니다.
> - 대신 원본은 "응력이 뭐야?" 같은 상식 질문까지 새 스킬로 보내는 **새로운 오발동**이 생겼습니다.
> - 마지막으로 web_research 설명에 **"찾아보지 않아도 답할 수 있는 상식 설명이나 조언에는 쓰지 않는다"는 경계 문장 하나**를 더했습니다. 실제 요청 정확도는 94.0%에서 **99.2%**로 올랐고, 실험에 쓰지 않았던 테스트셋에서도 87.5%에서 95.8%로 올랐습니다. 비용 증가는 2~16%였습니다.
> - **최종 판단: 기존 스킬 7개와 지시문은 원본 그대로 두고, web_research 스킬(경계 문장 포함)만 추가하는 설정을 채택합니다.** 자동 개선이 만든 지시문과 description은 쓰지 않습니다.
> - 같은 설정을 다시 돌리면 정확도가 3%p 정도 흔들렸습니다. 그래서 한 번의 실행으로 고른 "최고 설정"은 믿기 어렵다는 것도 함께 확인했습니다.

### 2. 측정 버그: 모델 탓이 아니었던 75%
- **증상**: v2 첫 실행이 15/20이었고, 틀린 5개는 전부 빈 답이었습니다.
- **원인 (추정)**: Haiku 5.5는 기본적으로 먼저 생각(thinking)을 합니다. 그런데 `max_tokens=50`이 너무 작아서, 애매한 요청에서 답을 쓰기 전에 잘린 것으로 봤습니다. 당시에는 `stop_reason`을 기록하지 않아 직접 확인하지는 못했습니다.
- **수정**: `max_tokens=1024`로 올리고, 빈 답과 `stop_reason`을 따로 기록하게 했습니다. 다른 설정은 그대로 두었는데 20/20이 나와서, 한도가 원인이었다고 판단했습니다.
- **교훈**: 평가 코드의 설정 하나가 모델 오류처럼 보일 수 있습니다. 그래서 이후 모든 결과에 빈 답 수, 목록 밖 답 수, `stop_reason`을 함께 남겼습니다.

effort(생각 깊이) 비교 (v2, 둘 다 20/20):

| effort | 출력 토큰 합계 |
|---|---|
| low | 158 |
| medium | 432 (2.7배) |

정확도가 같으므로 기본값은 `low`로 정했습니다.

### 3. v3에서 드러난 약점 (Haiku 5.5, effort low, 32케이스 × 3회)

|---|---|

| 두 스킬이 겹치는 요청 | 39/39 |

- **오발동 예시**: "요약을 잘하는 방법 알려줘" → summarize, "코딩 공부는 어떤 언어로 시작해?" → code_help. 둘 다 3번 모두 같은 오답이라, 우연이 아닌 체계적인 약점입니다.
- **원인**: 요청에 스킬과 관련된 단어가 나오면, 작업을 해 달라는 건지 그 주제를 묻는 건지 구분하지 않고 스킬을 골랐습니다.

### 4. 자동 개선 루프
- **라우터**: Haiku 5.5 / **개선 모델**: Opus 5.5
- **학습셋**: v3 32개 / **테스트셋**: 새로 만든 24개 (none 12개 + 비슷한 단어가 들어간 정상 요청 12개). 개선 모델은 테스트셋을 보지 않습니다.
- **채택 규칙**: 형식 검사(none 출력 규칙 유지, 한 줄 60자, 스킬 추가·삭제 금지)를 통과하고 학습셋 정확도가 오를 때만 채택합니다.
- **결과**: 첫 수정안이 바로 채택됐고 학습셋 100%에 도달해 1회 만에 끝났습니다.
- **개선 모델의 진단 (요약)**: 주제어가 나오기만 하면 그 스킬을 고르고, 작업 수행 요청과 조언·방법·추천 질문을 구분하지 못한다.
- **바뀐 지시문의 핵심 (요약)**: 사용자가 그 스킬의 작업을 지금 직접 해 달라고 할 때만 고른다. 공부법·요령·진로·도구 사용법·추천·일반 지식 질문이면 none. 원문은 `improve_runs/summary.json`의 `best_config`에 있습니다.
- **바뀐 description**: 학습셋에서 틀린 4개 스킬에 "주어진 / 직접" 같은 표현이 추가됐습니다. 원본 `skills/`는 수정하지 않았고, 개선본은 `improve_runs/summary.json`에 있습니다.

### 5. 원인 분리 실험과 비용 (Haiku 5.5, effort low, 각 케이스 2회)
| 조합 | 학습셋 (32×2) | 테스트셋 (24×2) | 테스트셋 오발동률 | 호출당 입력 토큰 | 1천 회당 비용 (학습셋 / 테스트셋) |
|---|---|---|---|---|---|
| 원본 | 85.9% | 91.7% | 16.7% | 298 | $0.043 / $0.048 |
| 지시문만 개선 | 98.4% | **100%** | 0% | 542 | $0.073 (+70%) / $0.058 (+21%) |
| description만 개선 | **100%** | 95.8% | 8.3% | 335 | $0.052 (+21%) / $0.039 (-19%) |

- 입력 토큰은 테스트셋 기준이고, 학습셋도 거의 같습니다.
- 비용이 학습셋과 테스트셋에서 크게 다른 건 출력 토큰(생각 포함) 때문입니다. 학습셋에서는 모든 조합이 26~37개로 비슷했고, 테스트셋에서는 개선 조합만 7~10개로 줄었습니다.
- 전체 표(누락률, 일관성, 토큰 수)는 [`improve_runs/ablation.md`](improve_runs/ablation.md)에 있습니다.

### 6. 발견한 점
1. **일반화는 지시문에서 나온 것으로 보입니다.**
   - 지시문만 고쳐도 테스트셋 100%였고, description만 고친 버전은 95.8%였습니다.
   - description만 고친 버전이 테스트셋에서 틀린 2회는 둘 다 "자주 틀리는 맞춤법 알려줘 → proofread"였습니다.
   - 개선 모델은 학습셋에서 틀린 4개 스킬의 description만 고쳤고, `proofread`는 손대지 않았습니다.
   - 그래서 **description 수정은 고친 스킬에만 효과가 있고, 지시문은 모든 스킬에 적용되는 것**으로 해석했습니다.
   - 다만 근거는 요청 1개(2회)입니다. description을 고치지 않은 `report_write`의 none 요청(#118)은 맞혔는데, 이 요청은 원본에서도 2회 중 1회만 틀렸습니다. 확인하려면 케이스가 더 필요합니다.
2. **지시문만 고치면 반대쪽 부작용이 생깁니다.**
   - "이 파이썬 코드가 내는 오류가 왜 생기는지 알려줘"를 none으로 답했습니다(누락).
   - "일반 지식 질문은 none"이라는 규칙이 자기 코드에 대한 "왜?" 질문까지 막은 경우입니다.
   - 둘 다 고친 버전에서는 사라졌으므로, 두 수정은 서로 보완합니다.
3. **정확도와 비용 사이에 선택지가 생겼습니다.**
   - 확실한 비용 차이는 입력 토큰입니다. description만 고치면 +12%, 지시문을 고치면 약 +80~95%입니다.
   - 둘 다 고친 버전은 가장 정확하지만 가장 비쌉니다(학습셋 +79%, 테스트셋 +30%).
   - description만 고친 버전은 비용이 가장 적게 늘지만 처음 보는 요청에서 오발동이 남았습니다.
   - 테스트셋에서 개선 조합의 비용이 낮게 나온 건 출력 토큰이 줄었기 때문인데, 학습셋에서는 줄지 않아 믿기 어렵습니다(한계 참고).
4. **원본 결과가 재현됐습니다.**
   - 자동 개선 실행과 원인 분리 실행에서 원본 성적이 학습셋 84.4% / 85.9%, 테스트셋 91.7% / 91.7%로 비슷했습니다.

### 7. 외부 테스트셋 (외부 참여자 3명, 30개 × 3회)
참여자 수는 요청 묶음 기준입니다. 2·3번째 묶음은 같은 사람이 썼을 수 있습니다.

실험에 참여하지 않은 사람들이 "AI 비서에게 할 법한 요청"을 평소 말투로 쓴 30개입니다(`cases_external.json`, 오타 포함 원문 그대로). 정답은 스킬 description 기준으로 붙였고, 애매한 요청 9개는 정답 후보를 여러 개 허용했습니다.

| 조합 | 정확도 | 누락률 | 일관성 | 호출당 출력 토큰 | 1천 회당 비용 |
|---|---|---|---|---|---|
| **원본** | **90/90 (100%)** | 0% | 96.7% | 34 | **$0.049** |
| 지시문만 개선 | 85/90 (94.4%) | 25.0% | 93.3% | 109 | $0.110 (+127%) |
| description만 개선 | 87/90 (96.7%) | 0% | 96.7% | 59 | $0.064 (+32%) |
| 둘 다 개선 | 84/90 (93.3%) | 33.3% | 86.7% | 117 | $0.118 (+143%) |

누락률은 스킬이 필요한 요청 4개(번역, 발표 대본, 엑셀, 지출 정리) × 3회 = 12회 중 none으로 답한 비율입니다.

1. **실제 요청은 대부분 스킬이 필요 없는 요청이었습니다.**
   - 30개 중 19개가 날씨, 뉴스, 지식 질문, 추천, 사진 편집 같은 요청이었습니다.
   - 스킬에 맞는 요청은 4개뿐이었습니다. 직접 만든 테스트셋(절반이 스킬 요청)과 분포가 크게 달랐습니다.
2. **원본은 실제 요청에서 오발동이 없었습니다.**
   - 확실한 none 요청 19개를 네 조합 모두 전부 맞혔습니다.
   - v3에서 본 오발동은 "요약을 잘하는 방법"처럼 스킬 단어를 일부러 넣은 요청에서만 나왔습니다. 실제 요청에서는 고칠 문제가 거의 없었던 셈입니다.
3. **개선이 새로운 오답을 만들었습니다.**
   - **"엑셀 잘 모르는데 이거 자동으로 계산되게 할 수 없나?"**: 지시문을 고친 두 버전 모두 3회 내내 none으로 답했습니다. 개선 지시문의 "도구 사용법 질문이면 none" 규칙에 걸린 것으로 보입니다. 원본은 data_analysis로 답했습니다.
   - **"AI글래스 이슈들 정리해줘"**: 개선본 세 버전 모두 report_write로 답한 경우가 있었습니다. 원본은 summarize로 일관됐습니다.
   - **"지출 정리 좀 해줘"**: 둘 다 고친 버전이 3회 중 1회 none으로 답했습니다.
4. **개선본은 경계 요청에서 더 망설이고 덜 재현됩니다.**
   - 1차 10개를 다시 돌렸을 때, 원본은 1차 실행과 선택이 완전히 같았습니다.
   - 개선본들은 1~4개 요청에서 선택이 달라졌습니다.
   - 출력 토큰(생각 포함)도 원본의 1.7~3.4배였습니다.
5. **결론**
   - 자동 개선은 측정한 문제(직접 만든 테스트셋의 주제어 오발동)는 고쳤습니다.
   - 하지만 실제 요청에서는 그 문제가 거의 없었고, 오히려 정상 요청을 놓치는 새 문제가 생겼습니다.
   - 개선을 채택할지는 학습셋이나 직접 만든 테스트셋이 아니라, 실제 사용에 가까운 검증셋으로 정해야 합니다.

1차(10개)만 돌린 결과는 `improve_runs/ablation_cases_external_round1.*`, 30개 전체 결과는 `improve_runs/ablation_cases_external.*`에 있습니다.

### 8. 검증셋 기준 자동 개선 (같은 설정으로 2회 실행)
외부 요청 30개를 검증셋 16개(`cases_val.json`)와 보류셋 14개(`cases_holdout.json`)로 나눴습니다.
- **채택 기준**: 학습셋 정확도가 오르고 **검증셋 정확도가 떨어지지 않을 때만** 채택합니다.
- **검증셋 비공개**: 개선 모델에게 검증셋 내용은 보여 주지 않고, "검증셋 점수가 떨어져 거절됐다"는 사실만 알려 줍니다.
- **보류셋**: 개선 과정에서 전혀 쓰지 않습니다.

| | 1회차 | 2회차 |
|---|---|---|
| 수정안 | 3개 모두 거절 (검증셋 100% → 93.8~96.9%) | 1번째 거절, 2번째 채택 (검증셋 100% 유지) |
| 최종 설정 | 원본 그대로 | 새 지시문 |
| 테스트셋 (직접 만든 24개) | 95.8% → 95.8% | 95.8% → **100%** |
| 보류셋 (실제 요청 14개) | 100% → 100% | 96.4% → **92.9%** |
| 보류셋 1천 회당 비용 | 변화 없음 | $0.051 → $0.115 (+124%) |

1회차 결과 파일은 2회차가 같은 이름으로 저장하면서 덮어써졌습니다. 그래서 1회차 숫자는 터미널 출력에서 옮겨 적었습니다([`improve_runs_val/run1_console.md`](improve_runs_val/run1_console.md)). 이후 `improve.py`는 기존 결과를 덮어쓰지 않고, 검증셋의 요청별 선택도 저장하도록 고쳤습니다.

1. **안전장치는 의도대로 작동했습니다.**
   - 거절된 수정안 4개는 모두 학습셋 점수를 올렸습니다(96.9~100%).
   - 하지만 검증셋에서는 스킬이 필요한 요청을 none으로 놓쳤습니다(누락률 25~50%).
   - 지난번 "엑셀 자동 계산" 회귀와 같은 패턴입니다. 다만 당시에는 검증셋의 요청별 기록을 남기지 않아서, 어떤 요청을 놓쳤는지까지는 확인하지 못했습니다.
2. **개선 모델은 내용을 보지 않고도 거절 이유에 반응했습니다.**
   - 2회차의 두 번째 수정안은 "이전 규칙이 질문 형태를 none으로 밀어서 실제 작업 요청까지 놓쳤을 것"이라고 스스로 추론했습니다.
   - 그래서 "자기 코드·데이터·글을 가리키며 묻는 경우는 질문 형태여도 작업 요청"이라는 반대 방향 규칙을 넣었고, 검증셋 100%를 유지했습니다.
3. **그래도 검증셋에 없는 유형은 막지 못했습니다.**
   - 2회차에서 채택된 설정은 보류셋의 "AI글래스에 대한 이슈들 정리해줘"를 2회 모두 report_write로 답했습니다.
   - 이 유형은 외부 테스트에서 이미 본 오답인데, 검증셋에는 비슷한 요청이 없어서 걸러지지 않았습니다.
   - **안전장치는 검증셋에 들어 있는 유형만 지켜 줍니다.**
4. **같은 설정으로 두 번 돌렸는데 결론이 달랐습니다.**
   - 1회차는 "원본 유지", 2회차는 "새 지시문 채택"이었습니다.
   - 개선 모델이 매번 다른 수정안을 내고, 라우터의 답도 경계 요청에서 흔들리기 때문입니다.
   - 한 번의 실행 결과로 채택을 결정하면 안 됩니다.
5. **비용 기준이 빠져 있었습니다.**
   - 2회차에서 채택된 지시문은 입력 토큰을 약 2.2배로 늘렸습니다.
   - 정확도 이득이 없는 데이터(보류셋)에서도 비용은 2배 이상이었습니다.

**최종 판단**
- 직접 만든 데이터에서는 개선이 분명했습니다.
- 하지만 실제 요청(검증셋 + 보류셋)에서는 원본이 이미 100%에 가깝고, 개선은 비용만 늘리거나 새 오답을 만들었습니다.
- 그래서 지금 근거로는 **원본 설정을 유지하는 것이 맞습니다.**

### 9. 외부 작업 요청 (외부 참여자 2명, 20개 × 3회)

- **결론**: 지금은 원본을 유지합니다. 지시문을 더 다듬기보다, 반복되는 오답의 원인인 **빠진 검색·조사 스킬을 추가하는 것**이 다음 개선 대상입니다.

### 11. 검색·조사 스킬 추가 (실제 요청 83개 + v3 32개, 각 3회)
10번까지 모든 실제 데이터에서 반복된 오답은 "조사해서 알려줘", "뉴스 정리해줘"가 report_write나 summarize로 새는 것이었습니다. 그래서 `skills_search/web_research`("웹에서 최신 정보나 자료를 찾아 조사해서 알려준다")를 추가했습니다.

**정답 기준을 먼저 정했습니다.**
- 10번에서 결과를 본 뒤 라벨 불일치를 발견한 일이 있어서, 이번에는 **평가 전에** 규칙(`LABELING.md`)과 번호별 라벨(`labels_search.json`)을 저장소에 먼저 올렸습니다.
- 규칙: 찾아봐야 답할 수 있는 요청(뉴스, 가격, 날씨, 제품 찾기, 회사·학교·논문 조사)은 web_research, 상식 설명과 생활 조언은 none입니다. 경계에 있는 요청(길 안내, 제품 추천)은 둘 다 허용합니다.
- 새 기준에 따라 친구분 자연 요청 11개와 본인 기록 22개의 라벨이 바뀌었습니다. 작업 요청과 v3는 바꾸지 않았습니다.
- 라벨이 달라졌으므로, 이 결과를 10번까지의 정확도와 그대로 비교하면 안 됩니다.

| 설정 | 친구 자연 30 | 친구 작업 20 | 본인 기록 33 | 실제 요청 합계 | v3 32 (회귀 확인) | 비용 (원본 대비) |
|---|---|---|---|---|---|---|
| 원본 | 95.6% | 100% | 92.9% | 95.6% | 84.4% | 기준 |
| 지시문만 개선 | 96.7% | 100% | 97.0% | 97.6% | **100%** | 1.5~2.3배 |
| **description만 개선** | **97.8%** | 100% | **98.0%** | **98.4%** | 95.8% | **1.1~1.2배** |
| 둘 다 개선 | 95.6% | 100% | 97.0% | 97.2% | **100%** | 1.5~2.3배 |

"개선"은 4번 자동 개선 루프가 만든 지시문과 description입니다. 이번에 새로 개선하지는 않았습니다.

1. **목표했던 문제는 해결됐습니다.**
   - 친구분 자연 요청에서 web_research가 정답 후보인 요청 11개를, 원본이 33회 중 32회 web_research로 보냈습니다.
   - 스킬을 추가하기 전에는 같은 요청이 summarize(12회)나 none(21회)으로 갔습니다.
   - 본인 기록에서 반복되던 "조사해서 알려줘 → report_write" 오답은 모든 설정에서 사라졌습니다.
2. **새로운 경계에서 오발동이 생겼습니다.**
   - 원본은 상식 질문과 생활 조언까지 web_research로 보냈습니다. "응력에 대해서 알려줘", "온디바이스 AI가 뭐야?", 다이어트 방법, 저녁 메뉴, 키높이 깔창 같은 요청입니다.
   - "찾아봐야 하는지, 아는 것으로 답하면 되는지"라는 경계가 새로 생긴 것입니다.
   - 원본의 일관성도 떨어졌습니다(본인 기록 69.7%, 친구 자연 요청 83.3%). 경계 요청에서 매번 답이 흔들렸습니다.
   - 친구 자연 요청에서는 원본의 출력 토큰이 34개에서 60개로 늘어, 비용이 스킬 추가 전보다 약 1.3배가 됐습니다.
3. **지시문을 고친 설정은 오발동을 없앴지만, 예전의 놓침이 다시 나왔습니다.**
   - "엑셀 자동으로 계산되게 할 수 없나?"를 3회 모두 none으로 답했습니다(7번과 같은 오답).
   - 링크를 주고 회사를 분석해 달라는 요청도 3회 모두 none으로 답했습니다.
   - 비용은 원본의 1.5~2.3배였습니다.
4. **description만 고친 설정이 가장 균형이 좋았습니다.**
   - 실제 요청 83개에서 가장 정확했고(98.4%), 비용 증가는 1.1~1.2배였습니다.
   - "주어진 글을 직접 요약한다", "요청한 코드를 직접 작성한다"처럼 **"직접 처리한다"를 강조한 설명**이, 상식 질문과 작업 요청을 가르는 데 도움이 된 것으로 보입니다.
   - 남은 오답은 "응력에 대해서 알려줘 → web_research"(2회) 같은 상식 질문 오발동입니다.
5. **주의할 점**
   - 네 설정 중 하나를 같은 데이터로 골랐으므로, 98.4%는 조금 부풀려졌을 수 있습니다. 새 데이터로 확인해야 합니다.
   - v3의 "맞춤법 검사기 중에 뭐가 제일 좋아?"는 규칙 3(제품 추천은 둘 다 허용)을 적용했어야 하는데, v3는 라벨을 바꾸지 않기로 해서 none만 정답으로 남았습니다. 이번에도 결과를 본 뒤 고치지 않고 적어 둡니다. web_research를 허용하면 원본은 87.5%, description만 개선한 설정은 99.0%가 됩니다.

본인 기록의 케이스 파일(`cases_history_search.json`)과 결과 파일은 이번에도 공개 저장소에 올리지 않았습니다.

### 12. web_research 경계 문장 (실제 요청 83개 + v3 32개 + 테스트셋 24개, 각 3회)
11번에서 새로 생긴 오발동(상식 질문 → web_research)을 줄이려고, web_research 설명에 경계 문장을 더했습니다.
- 기존: "웹에서 최신 정보나 자료를 찾아 조사해서 알려준다"
- 경계 문장 추가: "웹에서 최신 정보나 자료를 찾아 조사해서 알려준다. **찾아보지 않아도 답할 수 있는 상식 설명이나 조언에는 쓰지 않는다**"

**실행 전에 정한 것**
- 비교할 설정 4개(`configs_web_boundary.json`)와 정답 기준 v2(`labels_search2.json`)를 실행 전에 커밋했습니다.
- 정답 기준 v2에서는 11번에서 v3에 적용하지 않았던 규칙 3(제품 추천은 둘 다 정답)을 적용했습니다.
- web_research를 넣은 뒤 한 번도 평가하지 않은 테스트셋 24개를 추가했습니다. 경계 문장은 실제 요청의 오답을 보고 만든 것이라, 그 데이터와 별개로 확인하기 위해서입니다.
- 설정은 2×2로 짰습니다. A와 C를 비교하면 경계 문장 하나의 효과를, B와 D를 비교하면 개선된 description과 함께 쓸 때의 효과를 볼 수 있습니다.

| 설정 | 실제 요청 83개 | 본인 기록 첫 메시지 | v3 | 테스트셋 | 비용 (A 대비) |
|---|---|---|---|---|---|
| A 원본 | 94.0% | 95.2% | 89.6% | 87.5% | 기준 |
| B description 개선 | 95.2% | 90.5% | 96.9% | 87.5% | 1.06~1.26배 |
| **C 원본 + 경계 문장** | **99.2%** | **100%** | **100%** | 95.8% | **1.02~1.16배** |
| D description 개선 + 경계 문장 | **99.2%** | **100%** | **100%** | **97.2%** | 1.09~1.44배 |

1. **경계 문장 하나로 상식 질문 오발동이 거의 사라졌습니다.**
   - A와 C는 web_research 설명 한 문장만 다릅니다. 그런데 실제 요청 정확도가 94.0%에서 99.2%로 올랐습니다.
   - "응력에 대해서 알려줘", "저녁 뭐 먹을까?", 다이어트 방법, 선물 추천 같은 요청이 더는 web_research로 가지 않았습니다.
2. **반대 방향 실수는 없었습니다.**
   - 날씨, 뉴스, 요즘 챌린지, AI글래스 이슈처럼 찾아봐야 하는 요청은 네 설정 모두 web_research로 보냈습니다.
   - 경계 문장이 있는 설정이 none을 고른 것은 길 안내와 택스프리 방법처럼 원래 둘 다 정답인 요청뿐이었습니다.
3. **처음 평가한 테스트셋에서도 효과가 있었습니다.**
   - A 87.5% → C 95.8%. "데이터 분석가 자격증", "이메일 마케팅 효과" 같은 상식 질문의 오발동이 사라졌습니다.
   - 다만 테스트셋도 이 실험을 진행한 쪽에서 만든 데이터라, 완전히 독립된 확인은 아닙니다.
4. **11번의 "최고 설정"은 재현되지 않았습니다.**
   - 11번에서 98.4%였던 B(description 개선)가 이번에는 같은 데이터·같은 라벨로 95.2%였습니다.
   - 같은 설정이 실행마다 3%p 정도 흔들린다는 뜻입니다. 11번의 결론은 이 흔들림과 같은 데이터로 고른 효과가 섞인 결과였습니다.
5. **C를 채택합니다.**
   - C와 D는 실제 요청 정확도가 같고, 테스트셋 차이는 72회 중 1회입니다.
   - C는 바꾼 곳이 web_research 설명 한 문장뿐이라 가장 단순하고 가장 쌉니다.
   - D는 "엑셀 자동으로 계산되게 할 수 없나?"를 한 번 놓쳤고 비용이 더 듭니다.
6. **남은 오답**
   - "사람들이 자주 틀리는 맞춤법 몇 개 알려줘"를 A·B·C는 3회 모두, D는 3회 중 2회 proofread로 답했습니다. 고칠 글이 없는 지식 질문인데, 주제어(맞춤법)를 보고 고르는 예전 유형의 오발동입니다.
   - 본인 기록의 "정리해서 알려줘" 요청 하나를 C와 D가 3회 중 1회 web_research로 답했습니다. C는 대외활동 요청 하나도 3회 중 1회 data_analysis로 답했습니다.

경계 문장은 아직 `skills_search/web_research/SKILL.md`에 반영하지 않았습니다. 11번 결과를 그대로 재현할 수 있게 두었고, 채택한 설정은 `configs_web_boundary.json`의 "C 원본 + 경계 문장"입니다.

### 13. 한계
- **규모가 작습니다.**
  - 테스트셋 none 요청이 12개뿐입니다.
  - 조합 간 차이가 대부분 1~2회(테스트셋 48회 중)입니다.
  - 그래서 "경향"으로만 해석해야 합니다.
- **학습셋과 테스트셋을 같은 사람이 만들었습니다.**
  - 개선된 지시문의 "공부법·진로·도구 추천" 같은 표현이 테스트셋 none 요청과 유형이 비슷합니다.
  - 외부 테스트셋에서 실제로 분포 차이가 확인됐습니다. 외부 요청은 자연 요청 30개와 작업 요청 20개, 모두 50개입니다. 참여자 수는 요청 묶음 기준이라 실제보다 적을 수 있습니다.
- **개선이 1회 만에 끝났습니다.** 여러 번 반복하며 개선하는 과정은 아직 검증되지 않았습니다.
- **출력 토큰 해석에 주의가 필요합니다.** 개선본에서 테스트셋 출력 토큰이 줄었지만, 학습셋에서는 줄지 않았습니다. "명확한 지시문이 생각을 줄인다"고 결론 내리기에는 근거가 부족합니다.
- **정답 라벨은 description을 기준으로 사람이 판단한 것입니다.** 애매한 요청은 정답 후보를 여러 개(`acceptable`) 허용했습니다. 예를 들어 "엑셀 자동 계산되게 할 수 없나?"는 code_help와 data_analysis를 정답으로 봤는데, 방법을 묻는 질문으로 보면 none도 가능하다는 반론이 있을 수 있습니다.

### 14. 다음 과제
- 검증셋이 실제 오답 유형(예: "이슈 정리해줘" → report_write)을 빠짐없이 담도록 외부 요청을 더 모으기
- 자동 개선을 여러 번 실행해, 여러 번 모두 통과한 수정안만 채택하기
- **(가장 먼저)** 채택한 설정(원본 + 경계 문장 web_research)을 새로 모은 실제 요청으로 확인하기
- 같은 설정을 여러 번 실행해 평균과 흔들림 폭을 함께 보고하기 (12번에서 실행마다 3%p 정도 흔들림을 확인)
- "자주 틀리는 맞춤법 알려줘 → proofread"처럼 고칠 대상이 없는 지식 질문의 오발동 줄이기
- 스킬 수를 늘렸을 때(20개 이상) 오선택과 비용이 어떻게 변하는지 측정
- 채택 기준에 비용을 넣기 (예: 검증셋 정확도 이득이 없으면 토큰이 늘어난 수정안은 거절)

```bash
python3 improve.py --dry-run                                        # 자동 개선 루프, API 없이 흐름만 확인
python3 improve.py                                                  # 자동 개선 루프
python3 ablation.py                                                 # 원인 분리 실험
python3 improve.py --val cases_val.json --holdout cases_holdout.json --outdir improve_runs_val   # 검증셋 기준 자동 개선
```

`improve.py`에 `--val`을 주면, 수정안은 **학습셋 정확도가 오르고 검증셋 정확도가 떨어지지 않을 때만** 채택됩니다.
개선 모델에게 검증셋 내용은 보여 주지 않고, "검증셋 점수가 떨어져 거절됐다"는 사실만 알려 줍니다.
`--holdout`은 개선 과정에서 전혀 쓰지 않고 마지막 비교에만 씁니다.

`extract_history.py`는 챗GPT·Claude에서 내보낸 `conversations.json`에서 실험 시작 전 대화의 첫 요청만 무작위로 뽑습니다. 이메일·전화번호·링크는 자동으로 가립니다. 기록 파일과 결과 파일(`history_requests.txt`)은 `.gitignore`에 들어 있어 커밋되지 않습니다.

`eval.py` 옵션: `--effort low|medium|high` (기본 low), `--repeats N`, `--model`, `--out`

다른 케이스 파일 하나로 네 조합(원본 / 지시문만 / description만 / 둘 다)을 평가하려면 `--cases`를 씁니다.
결과는 `improve_runs/ablation_<파일이름>.md`에 저장됩니다.
```bash
python3 ablation.py --cases cases_external.json
```

## 지표
- **정확도**: 전체와 케이스 종류별(clear / overlap / ambiguous / none)
- **스킬별 정밀도·재현율**, 혼동 행렬
- **오발동률**: 스킬이 필요 없는데 스킬을 고른 비율
- **누락률**: 스킬이 필요한데 none 을 고른 비율
- **목록 밖 답변 수 / 빈 답변 수**: 빈 답변은 `stop_reason`을 함께 기록
- **일관성**: 같은 요청을 반복했을 때 매번 같은 답을 한 케이스의 비율

케이스 파일 규칙:
- `overlap` 케이스에는 헷갈리기 쉬운 스킬을 `confusable` 필드로 적었습니다.
- `ambiguous` 케이스는 `acceptable` 목록에 든 답이면 정답으로 칩니다.
- 케이스 파일의 `skills_dirs`로 어떤 스킬 폴더를 쓸지 정합니다.
