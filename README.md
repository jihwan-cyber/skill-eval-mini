# skill-eval-mini

AI 에이전트의 **스킬 선택**을 평가하고 자동으로 개선하는 축소판 실험입니다.
라우터 모델은 각 스킬의 `name`과 `description`만 보고, 사용자 요청마다 스킬 하나 또는 `none`을 고릅니다.

> **한 줄 요약**: 라우터(Claude Haiku 5.5)의 약점은 비슷한 스킬끼리의 혼동이 아니라 **오발동**이었습니다. 주제만 겹치는 질문에도 스킬을 고르는 문제예요.
> 자동 개선 루프로 처음 보는 테스트셋의 정확도를 **91.7% → 100%**(오발동 16.7% → 0%)로 올렸습니다.
> 원인 분리 실험에서는 **지시문 수정이 일반화를 만들었고, description 수정은 학습셋에 맞춰지는 경향**을 확인했습니다. 대가는 호출당 입력 토큰 약 2배, 호출 비용 +30~79%입니다.

## 결과 보고서

### 1. 진행 과정
| 단계 | 한 일 | 알게 된 것 |
|---|---|---|
| v1 | 스킬 3개, 9케이스 (`run.py`) | 기본 파이프라인 확인 |
| v2 | 스킬 5개를 `SKILL.md`로 분리, 지표 확장 (`eval.py`) | 첫 실행 75%. 하지만 원인은 **측정 버그**였음 (아래 2번) |
| v3 | 헷갈리는 스킬 2개 추가, 어려운 32케이스, 3회 반복 | 비슷한 스킬끼리는 전부 맞힘. **틀린 13회가 모두 오발동** |
| 자동 개선 | 틀린 케이스로 지시문·description을 고치고, 좋아질 때만 채택 (`improve.py`) | 학습셋과 처음 보는 테스트셋 모두 100% |
| 원인 분리 | 지시문 / description을 나눠 효과와 비용 비교 (`ablation.py`) | 일반화는 지시문, description은 과적합 경향 |

### 2. 측정 버그: 모델 탓이 아니었던 75%
- **증상**: v2 첫 실행이 15/20이었고, 틀린 5개는 전부 빈 답이었습니다.
- **원인 (추정)**: Haiku 5.5는 기본적으로 먼저 생각(thinking)을 합니다. 그런데 `max_tokens=50`이 너무 작아서, 애매한 요청에서 답을 쓰기 전에 잘린 것으로 봤습니다. 당시에는 `stop_reason`을 기록하지 않아 직접 확인하지는 못했습니다.
- **수정**: `max_tokens=1024`로 올리고, 빈 답과 `stop_reason`을 따로 기록하게 했습니다. 다른 설정은 그대로 두었는데 20/20이 나와서, 한도가 원인이었다고 판단했습니다.
- **교훈**: 평가 코드의 설정 하나가 모델 오류처럼 보일 수 있습니다. 그래서 이후 모든 결과에 빈 답 수, 목록 밖 답 수, `stop_reason`을 함께 남겼습니다.

effort(생각 깊이) 비교 (v2, 둘 다 20/20):

| effort | 출력 토큰 합계 |
|---|---|
| low | 158 |
| medium | 432 (2.7배) |

정확도가 같으므로 기본값은 `low`로 정했습니다.

### 3. v3에서 드러난 약점 (Haiku 5.5, effort low, 32케이스 × 3회)
| 케이스 종류 | 정확도 |
|---|---|
| 명확한 요청 | 21/21 |
| 두 스킬이 겹치는 요청 | 39/39 |
| 정답이 둘일 수 있는 애매한 요청 | 12/12 |
| **해당 없음(none)** | **11/24 (오발동률 54%)** |

- **오발동 예시**: "요약을 잘하는 방법 알려줘" → summarize, "코딩 공부는 어떤 언어로 시작해?" → code_help. 둘 다 3번 모두 같은 오답이라, 우연이 아닌 체계적인 약점입니다.
- **원인**: 요청에 스킬과 관련된 단어가 나오면, 작업을 해 달라는 건지 그 주제를 묻는 건지 구분하지 않고 스킬을 골랐습니다.

### 4. 자동 개선 루프
- **라우터**: Haiku 5.5 / **개선 모델**: Opus 5.5
- **학습셋**: v3 32개 / **테스트셋**: 새로 만든 24개 (none 12개 + 비슷한 단어가 들어간 정상 요청 12개). 개선 모델은 테스트셋을 보지 않습니다.
- **채택 규칙**: 형식 검사(none 출력 규칙 유지, 한 줄 60자, 스킬 추가·삭제 금지)를 통과하고 학습셋 정확도가 오를 때만 채택합니다.
- **결과**: 첫 수정안이 바로 채택됐고 학습셋 100%에 도달해 1회 만에 끝났습니다.
- **개선 모델의 진단 (요약)**: 주제어가 나오기만 하면 그 스킬을 고르고, 작업 수행 요청과 조언·방법·추천 질문을 구분하지 못한다.
- **바뀐 지시문의 핵심 (요약)**: 사용자가 그 스킬의 작업을 지금 직접 해 달라고 할 때만 고른다. 공부법·요령·진로·도구 사용법·추천·일반 지식 질문이면 none. 원문은 `improve_runs/summary.json`의 `best_config`에 있습니다.
- **바뀐 description**: 학습셋에서 틀린 4개 스킬에 "주어진 / 직접" 같은 표현이 추가됐습니다. 원본 `skills/`는 수정하지 않았고, 개선본은 `improve_runs/summary.json`에 있습니다.

### 5. 원인 분리 실험과 비용 (Haiku 5.5, effort low, 각 케이스 2회)
| 조합 | 학습셋 (32×2) | 테스트셋 (24×2) | 테스트셋 오발동률 | 호출당 입력 토큰 | 1천 회당 비용 (학습셋 / 테스트셋) |
|---|---|---|---|---|---|
| 원본 | 85.9% | 91.7% | 16.7% | 298 | $0.043 / $0.048 |
| 지시문만 개선 | 98.4% | **100%** | 0% | 542 | $0.073 (+70%) / $0.058 (+21%) |
| description만 개선 | **100%** | 95.8% | 8.3% | 335 | $0.052 (+21%) / $0.039 (-19%) |
| 둘 다 개선 | 100% | 100% | 0% | 579 | $0.077 (+79%) / $0.062 (+30%) |

- 입력 토큰은 테스트셋 기준이고, 학습셋도 거의 같습니다.
- 비용이 학습셋과 테스트셋에서 크게 다른 건 출력 토큰(생각 포함) 때문입니다. 학습셋에서는 모든 조합이 26~37개로 비슷했고, 테스트셋에서는 개선 조합만 7~10개로 줄었습니다.
- 전체 표(누락률, 일관성, 토큰 수)는 [`improve_runs/ablation.md`](improve_runs/ablation.md)에 있습니다.

### 6. 발견한 점
1. **일반화는 지시문에서 나온 것으로 보입니다.**
   - 지시문만 고쳐도 테스트셋 100%였고, description만 고친 버전은 95.8%였습니다.
   - description만 고친 버전이 테스트셋에서 틀린 2회는 둘 다 "자주 틀리는 맞춤법 알려줘 → proofread"였습니다.
   - 개선 모델은 학습셋에서 틀린 4개 스킬의 description만 고쳤고, `proofread`는 손대지 않았습니다.
   - 그래서 **description 수정은 고친 스킬에만 효과가 있고, 지시문은 모든 스킬에 적용되는 것**으로 해석했습니다.
   - 다만 근거는 요청 1개(2회)입니다. description을 고치지 않은 `report_write`의 none 요청(#118)은 맞혔는데, 이 요청은 원본에서도 2회 중 1회만 틀렸습니다. 확인하려면 케이스가 더 필요합니다.
2. **지시문만 고치면 반대쪽 부작용이 생깁니다.**
   - "이 파이썬 코드가 내는 오류가 왜 생기는지 알려줘"를 none으로 답했습니다(누락).
   - "일반 지식 질문은 none"이라는 규칙이 자기 코드에 대한 "왜?" 질문까지 막은 경우입니다.
   - 둘 다 고친 버전에서는 사라졌으므로, 두 수정은 서로 보완합니다.
3. **정확도와 비용 사이에 선택지가 생겼습니다.**
   - 확실한 비용 차이는 입력 토큰입니다. description만 고치면 +12%, 지시문을 고치면 약 +80~95%입니다.
   - 둘 다 고친 버전은 가장 정확하지만 가장 비쌉니다(학습셋 +79%, 테스트셋 +30%).
   - description만 고친 버전은 비용이 가장 적게 늘지만 처음 보는 요청에서 오발동이 남았습니다.
   - 테스트셋에서 개선 조합의 비용이 낮게 나온 건 출력 토큰이 줄었기 때문인데, 학습셋에서는 줄지 않아 믿기 어렵습니다(한계 참고).
4. **원본 결과가 재현됐습니다.**
   - 자동 개선 실행과 원인 분리 실행에서 원본 성적이 학습셋 84.4% / 85.9%, 테스트셋 91.7% / 91.7%로 비슷했습니다.

### 7. 한계
- **규모가 작습니다.**
  - 테스트셋 none 요청이 12개뿐입니다.
  - 조합 간 차이가 대부분 1~2회(테스트셋 48회 중)입니다.
  - 그래서 "경향"으로만 해석해야 합니다.
- **학습셋과 테스트셋을 같은 사람이 만들었습니다.**
  - 개선된 지시문의 "공부법·진로·도구 추천" 같은 표현이 테스트셋 none 요청과 유형이 비슷합니다.
  - 다른 사람이 쓴 요청이나 실제 사용 기록으로 다시 확인해야 합니다.
- **개선이 1회 만에 끝났습니다.** 여러 번 반복하며 개선하는 과정은 아직 검증되지 않았습니다.
- **출력 토큰 해석에 주의가 필요합니다.** 개선본에서 테스트셋 출력 토큰이 줄었지만, 학습셋에서는 줄지 않았습니다. "명확한 지시문이 생각을 줄인다"고 결론 내리기에는 근거가 부족합니다.
- **정답 라벨은 description을 기준으로 사람이 판단한 것입니다.** 애매한 요청은 정답 후보를 여러 개(`acceptable`) 허용했습니다.

### 8. 다음 과제
- 다른 사람이 쓴 요청과 실제 사용 기록으로 외부 테스트셋을 만들어 일반화를 다시 확인
- 스킬 수를 늘렸을 때(20개 이상) 오선택과 비용이 어떻게 변하는지 측정
- 채택 기준에 비용을 넣기 (예: 정확도가 같으면 토큰이 적은 쪽을 채택)
- 학습셋이 아닌 검증셋으로 채택 여부를 정해 과적합 줄이기

## 구성
| 파일 | 역할 |
|---|---|
| `skills/<name>/SKILL.md` | 평가 대상 스킬 5개 (frontmatter: name, description) |
| `skills_extra/<name>/SKILL.md` | v3용 헷갈리는 스킬 2개 (report_write, proofread) |
| `load_skills.py` | SKILL.md 를 읽어 `{name: description}` 으로 반환. 잘못된 파일은 경고 후 건너뜀 |
| `cases_v2.json` | 20개: clear 10 / overlap 6 / none 4 (스킬 5개) |
| `cases_v3.json` | 32개: clear 7 / overlap 13 / ambiguous 4 / none 8 (스킬 7개). 자동 개선의 학습셋 |
| `cases_test.json` | 24개: 자동 개선의 테스트셋 (개선 모델은 보지 않음) |
| `eval.py` | 선택기를 바꿔 끼워 평가하고 지표를 계산 |
| `improve.py` | 자동 개선 루프 |
| `ablation.py` | 원인 분리 실험과 비용 비교 |
| `results_*.json`, `improve_runs/` | 실제 API 실행 결과 |
| `run.py`, `cases.json` | v1 (스킬 3개, 9케이스) |

## 실행
`ANTHROPIC_API_KEY`가 필요한 명령과 API 없이 도는 명령이 있습니다.

```bash
python3 eval.py --selector keyword                                  # API 없이 도는 키워드 기준선
python3 eval.py --selector api                                      # v2
python3 eval.py --selector api --cases cases_v3.json --repeats 3    # v3, 3회 반복
python3 improve.py --dry-run                                        # 자동 개선 루프, API 없이 흐름만 확인
python3 improve.py                                                  # 자동 개선 루프
python3 ablation.py                                                 # 원인 분리 실험
```

`eval.py` 옵션: `--effort low|medium|high` (기본 low), `--repeats N`, `--model`, `--out`

## 지표
- **정확도**: 전체와 케이스 종류별(clear / overlap / ambiguous / none)
- **스킬별 정밀도·재현율**, 혼동 행렬
- **오발동률**: 스킬이 필요 없는데 스킬을 고른 비율
- **누락률**: 스킬이 필요한데 none 을 고른 비율
- **목록 밖 답변 수 / 빈 답변 수**: 빈 답변은 `stop_reason`을 함께 기록
- **일관성**: 같은 요청을 반복했을 때 매번 같은 답을 한 케이스의 비율

케이스 파일 규칙:
- `overlap` 케이스에는 헷갈리기 쉬운 스킬을 `confusable` 필드로 적었습니다.
- `ambiguous` 케이스는 `acceptable` 목록에 든 답이면 정답으로 칩니다.
- 케이스 파일의 `skills_dirs`로 어떤 스킬 폴더를 쓸지 정합니다.
